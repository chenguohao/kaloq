# 开发前准备清单 · 写代码之前要备齐什么

> 目标：第一行代码写下去之前，**不会因为缺账号、缺密钥、缺决定而停工**。  
> 对应 [platform-sketch.md](platform-sketch.md) 里的「阶段 0 开门」，预计 2–6 周，大部分时间在等两家通道回复。  
> 范围按第一期：美元（Pyvio）+ Tron 上的 USDT（Actyve），见 [aggregation-requirements.md](aggregation-requirements.md) 第 5 节。

---

## 0. 一眼看懂：哪些会卡住开发

不是每件事都要等齐才开工。按「卡不卡」分三档：

| 档 | 意思 | 例子 |
|----|------|------|
| 🔴 不齐不能开工 | 缺了就写不下去，或写了要推倒重来 | 沙箱账号、4 个产品决定、技术栈 |
| 🟡 开工后并行补 | 不影响先写骨架，但联调前必须有 | 固定出口 IP、webhook 公网地址、监控 |
| 🟢 上线前补齐 | 只影响上生产 | 生产账号、合同、应急预案 |

**关键路径**：向两家要沙箱账号 → 拿到后才能联调。所以**第一天就发邮件**，其它事情在等回复的时候做。

## 1. 商务与合同（负责人：商务 / 老板）

| # | 要做的事 | 档 | 产出 |
|---|----------|----|------|
| 1.1 | 联系 Pyvio、Actyve 的 BD，说明我们要做「聚合 API」 | 🔴 | 对接人、群聊 |
| 1.2 | 问清**客户的钱挂在谁名下**：用 Pyvio **机构模式**（每个客户单独实名、单独一个 Unit），还是**大商户模式**（全挂在我们公司名下）；Actyve 同样问一遍 | 🔴 | 书面答复 |
| 1.3 | 要两份费率表（收款、付款、换汇、链上网络费、月费、保证金），清单见 [pricing.md](pricing.md) 第 3 节 | 🟡 | 费率表 |
| 1.3b | 把「专用提价/分成后台、VA 入账三方拆分」写成邮件或合同；沙箱打一笔验证（见 [pricing.md](pricing.md) 第 4 节） | 🔴 | 书面 + 沙箱拆分凭证 |
| 1.4 | 签合作协议 / NDA | 🟢 | 合同 |
| 1.5 | 我们公司自己完成两家的 KYB（企业实名）材料 | 🔴 | 营业执照、股东、董事等材料提交 |

**为什么 1.2 必须问**：接口调用上没区别，区别在「钱算谁的」。如果用大商户模式，把很多客户的钱都收进我们一个账户，通道看到的是「我们公司在替别人收钱付钱」，这通常要支付牌照，一般商户协议也不允许。万一其中一个客户出了可疑交易，通道会冻结我们整个账户，所有客户一起停。机构模式下每个客户各自实名、各自一个格子，出事只影响他自己。

## 2. 合规与法律（负责人：老板 + 律师）

| # | 要做的事 | 档 | 产出 |
|---|----------|----|------|
| 2.1 | 确认**钱从头到尾都在通道那边**，我们只记账、不碰客户资金 | 🔴 | 律师意见 |
| 2.2 | 如果钱要经过我们的账户 → 评估需要什么牌照（这会比写代码贵得多） | 🔴 | 结论：要 / 不要 |
| 2.3 | 客户 KYC 谁负责：用通道的 KYC，还是合作方先做一层 | 🔴 | 书面约定 |
| 2.4 | 禁止的国家 / 行业名单（制裁、赌博等），从两家拿 | 🟡 | 名单 |
| 2.5 | 用户协议、隐私政策草稿（对合作方） | 🟢 | 文档 |

## 4. 通道账号与沙箱（负责人：后端）

### 4.1 两家都要

| # | 要做的事 | 档 |
|---|----------|----|
| 4.1.1 | 拿沙箱 `app_id`、`app_secret` | 🔴 |
| 4.1.2 | 自己生成 RSA 密钥对（PKCS8、2048 位），把**公钥**发给对方 | 🔴 |
| 4.1.3 | 拿对方的**平台公钥**（用来验回调签名） | 🔴 |
| 4.1.4 | 报沙箱 IP 白名单（见第 6 节固定出口 IP） | 🟡 |
| 4.1.5 | 报 webhook 回调地址（要公网 HTTPS） | 🟡 |
| 4.1.6 | 要一份沙箱**模拟入金**的方法（不然测不了收款） | 🔴 |
| 4.1.7 | 要完整的错误码表、限流规则、回调重试规则 | 🟡 |

生成密钥示例（私钥只留在我们服务器，不发给任何人）：

```bash
openssl genrsa -out merchant_private.pem 2048
openssl pkcs8 -topk8 -nocrypt -in merchant_private.pem -out merchant_private_pkcs8.pem
openssl rsa -in merchant_private.pem -pubout -out merchant_public.pem
```

### 4.2 必须让 Pyvio 单独开通的

完整表见 [EOPay.md 第 7 节](EOPay.md)。第一期务必书面要到：机构模式、自己的沙箱 AppID、分成后台、内部转账 Transfer、平台主 Unit、白标转售、IP 白名单、Webhook、Mock 入金、美元 VA 和银行付款范围。

### 4.3 Actyve 另外要问

- 开通 Tron 链 USDT
- **一人一地址**：能否按客户生成长期有效的独立收款地址（见 [EOPay.md](EOPay.md) 1.2 / 7.5）。公开 `getAccount` 只有商户各链一条，不能给 100 个用户共用
- 公开文档没写全的字段：Create Acquire 请求参数、Payee / Chain Payee 字段（见 [vendor-research.md](vendor-research.md) 第 7 节）
- 沙箱用的是测试网还是模拟数据？怎么拿测试币
- 提现到链上地址的网络费怎么扣、从哪个余额扣

## 5. 技术选型（负责人：后端，第一周定）

两个仓库目前都只有文档，还没有代码。按「最简单、够用」原则，建议：

| 项 | 建议 | 理由 |
|----|------|------|
| 语言框架 | 团队最熟的一种（Java Spring Boot / Go / Node NestJS 都行） | 支付系统最怕踩生坑，用熟的 |
| 数据库 | PostgreSQL | 账本要事务，金额用 `numeric`，不用浮点数 |
| 队列 | 第一期用数据库表 + 定时任务代替 | 少一个组件，出问题好查 |
| 部署 | 1 台应用服务器 + 托管数据库 | 见 [server-architecture.md](server-architecture.md) 6.1 |
| 代码仓库 | 本仓库加 `src/`，或新建代码仓库 | 二选一，定下来就行 |

要定下来的规矩：

- [ ] 金额一律用字符串传、用十进制存，写死每个币种的小数位（USD 2 位，USDT 6 位）
- [ ] 所有时间存 UTC
- [ ] 每个对外写接口都要带幂等键
- [ ] 分支和提交规范、代码评审规则

## 6. 服务器与基础设施（负责人：后端 / 运维）

| # | 要做的事 | 档 | 说明 |
|---|----------|----|------|
| 6.1 | 云账号、选区域（建议离两家服务器近，如香港 / 新加坡） | 🔴 | |
| 6.2 | **固定出口 IP**（弹性 IP 或 NAT 网关） | 🟡 | 两家都要 IP 白名单 |
| 6.3 | 域名 + HTTPS 证书，分出 `api.`、`hooks.`、`admin.` | 🟡 | 回调必须公网 HTTPS |
| 6.4 | 三套环境：本地开发、测试（连沙箱）、生产 | 🟡 | 生产密钥**只**放生产 |
| 6.5 | 密钥存放：云的密钥管理服务或加密配置，不进代码仓库 | 🔴 | |
| 6.6 | 数据库自动备份 + 试一次恢复 | 🟢 | |
| 6.7 | 日志、报警（接口报错、回调失败、对账不平要发消息） | 🟡 | |
| 6.8 | 本地开发能收到回调：用内网穿透工具（如 ngrok）临时代替 | 🟡 | |

## 8. 测试准备（负责人：后端 + 测试）

- [ ] 列出沙箱必测场景：开户通过 / 打回、美元入金、USDT 入金、付款成功、付款失败、付款超时、同一回调重复来、回调签名不对
- [ ] 准备测试数据：测试客户资料、测试银行账户、Tron 测试地址
- [ ] 准备一个「假合作方」接收我们的通知，用来看推送和重试
- [ ] 约定上线前的验收标准（参考 [aggregation-requirements.md](aggregation-requirements.md) 第 7 节）

## 9. 运营准备（负责人：运营，上线前完成）

- [ ] 谁看后台、谁有权限手动处理异常单（至少两人，操作要留记录）
- [ ] 对账不平的处理流程：谁看、多久内处理、怎么找通道
- [ ] 两家通道的紧急联系人和工单渠道
- [ ] 合作方接入流程：怎么发密钥、怎么配置通知地址、沙箱怎么给他们用
- [ ] 应急预案：通道宕机、私钥泄露、错付款时怎么办

## 10. 人员

第一期最少配置：

| 角色 | 人数 | 主要干什么 |
|------|------|------------|
| 后端 | 1（最好 2） | 第 4–8 节 |
| 商务 / 老板 | 兼职 | 第 1–3 节，对接两家 BD |
| 律师 | 外包 | 第 2 节 |
| 测试 / 运营 | 兼职 | 第 8–9 节 |

只有 1 名后端时，**一定要有第二个人看付款相关的代码**，钱的事不能只一个人看。

## 11. 建议顺序（按周）

| 周 | 做什么 |
|----|--------|
| 第 1 周 | 给两家发邮件要沙箱（1.1）；内部拍板第 3 节；定技术栈（5）；开云账号（6.1） |
| 第 2 周 | 提交 KYB 材料（1.5）；生成密钥、交公钥（4.1.2）；写对外 API 文档初稿（7.1） |
| 第 3–4 周 | 拿到沙箱后配白名单和回调；写状态机、字段映射、表设计（7.2–7.5）；搭项目骨架 |
| 等到沙箱 | 开始阶段 1 开发 |

**判断「准备好了」**：第 3 节 6 个问题都有答案，两家沙箱都能调通一个「查余额」接口，就可以正式开工。
