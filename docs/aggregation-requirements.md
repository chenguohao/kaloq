# 聚合需求澄清 · 把 Pyvio 和 Actyve 合成一套

> **本文只讲产品是什么，不写代码、不估工期。**  
> 目的：把「聚合」说清楚——合作方眼里是一个支付 API，底下再分别调两家。

---

## 1. 一句话

我们做一个 **支付聚合层**。

合作方只认识我们。他们创建一个客户、拿收款方式、看余额、发起付款、接收通知。他们 **不知道、也不需要知道** 底下是 Pyvio 还是 Actyve。

两家是通道：

| 通道 | 在我们产品里负责什么 |
|------|----------------------|
| **Pyvio** | 法币：银行收款账户、银行付款、法币换汇、以后的收银台和虚拟卡 |
| **Actyve** | 稳定币：链上收款地址、链上入金、链上出金，以及稳定币兑成美元/港币后再付银行 |

聚合的意思不是「把两份文档贴在一起」，而是：**对外一套对象、一套接口、一套通知；对内按「这笔钱是法币还是稳定币」路由到对应通道。**

---

## 2. 聚合到底聚什么

### 2.1 聚成什么（合作方看到的）

合作方眼里只有这些东西：

| 我们的对象 | 人话 |
|------------|------|
| **商户** | 调我们 API 的那一方（合作方自己） |
| **客户** | 商户下面的一个终端用户或企业（一个 KYC 主体） |
| **钱包** | 这个客户名下、按币种分开的余额（USD、USDT…） |
| **收款方式** | 怎么收钱：银行账号，或链上地址 |
| **付款单** | 从钱包把钱打出去 |
| **通知** | 钱到了、付款成功或失败 |

没有「Pyvio 客户」「Actyve 地址」这种对外名词。那些只存在于我们内部的映射表里。

### 2.2 不聚什么（别误解）

| 误解 | 正确说法 |
|------|----------|
| 把两家接口原样转发出去 | 不对。对外是我们自己的接口，字段和状态都统一 |
| 两家余额自动合成一个「总余额」随便花 | 不对。第一期按币种分开；跨形态（USDT→USD）要显式兑换或走通道支持的路径 |
| 我们自己发银行账号、自己管私钥 | 不对。账号和地址仍由通道开出，我们只做编排和记账 |
| 做成和 BVNK 一模一样的一站式 | 不对。能力边界由两家实际开通的产品决定；我们是编排层 |

### 2.3 结构（不用复杂流程图）

就三层。底下没有第四层。以前那块空白是画图工具画坏了，不是漏了内容。

```
合作方只看见
┌─────────────────────────────────────────┐
│  创建客户 · 开通收款方式 · 查余额 · 发起付款 · 收通知  │
└────────────────────┬────────────────────┘
                     ▼
我们 · 聚合层
┌─────────────────────────────────────────┐
│  路由与编排 · 客户↔通道映射 · 自有账本              │
└───────────┬─────────────────┬───────────┘
            ▼                 ▼
     ┌────────────┐    ┌────────────┐
     │ Actyve     │    │ Pyvio      │
     │ 稳定币      │    │ 法币        │
     └────────────┘    └────────────┘
            ▲                 ▲
            └────────┬────────┘
                     │ 两边 webhook
                     ▼
              验签 → 入账 → 统一通知合作方
```

银行和链都在 Pyvio / Actyve 里面，我们不画、也不自建。

我们自己服务器怎么拆、怎么部署，见 [server-architecture.md](server-architecture.md)。

## 3. 统一后的资金故事

用合作方能听懂的话讲完整条故事。

### 3.1 开户

商户为我们下面的某个「客户」提交资料。  
我们在内部完成通道侧需要的开户（主要走 Pyvio 的 KYC / Unit；稳定币地址挂在同一客户上）。  
对外只回：客户状态 = 审核中 / 可用 / 需补材料。

### 3.2 收款（两种入口，一个客户）

同一个客户可以同时有：

| 收款方式 | 给谁用 | 钱进哪里 |
|----------|--------|----------|
| **银行收款账户**（如美元账号） | 买家银行打款、平台结算 | 记入该客户的 **USD 钱包**（通道侧在 Pyvio） |
| **链上地址**（如 Tron USDT） | 对方钱包转稳定币 | 记入该客户的 **USDT 钱包**（通道侧在 Actyve） |

合作方给买家看的是「收款账号」或「收款地址」，不出现通道名。

### 3.3 余额（对外统一，对内分轨）

对外：`GET 钱包` → 列出该客户各币种可用余额。

对内：

- USD / HKD / EUR… 的真相在 Pyvio 钱包  
- USDT / USDC 的真相在 Actyve 地址余额  
- **我们自己再记一本账**，用来：入金确认、付款占用、对账、给合作方的通知

第一期默认规则：

- **同币种**才能直接付（USD 付美元银行；USDT 付 USDT 地址）  
- **跨形态**（USDT → 付美元银行）算单独能力：要么走 Actyve 的「提到银行 / GlobalAccount」，要么先兑换再付；**产品上要单独命名，不能假装余额已经混在一起**

### 3.4 付款（一个「发起付款」，底下分流）

合作方只调：`创建付款单`（金额、币种、收款人）。

我们按规则路由：

| 出款币种 / 目标 | 走谁 |
|-----------------|------|
| 法币 → 银行账户 | Pyvio 付款 |
| 稳定币 → 链上地址 | Actyve 链上提现 |
| 稳定币 → 银行账户 | Actyve 银行提现（若已开通） |
| 稳定币 → 法币全球账户 | Actyve 的 GlobalAccount（**待商务确认是否等于 Pyvio**） |

合作方只看到：处理中 / 成功 / 失败。看不到 Pyvio 单号或 Actyve 单号（内部可保留，运营查问题用）。

### 3.5 通知（一套事件）

不管钱从银行进还是从链上进，合作方只收我们定义的事件，例如：

- `customer.updated`（审核通过 / 打回）  
- `collection.succeeded`（某笔入金到账）  
- `payout.succeeded` / `payout.failed`  
- `wallet.updated`（可选）

事件里带我们的客户 ID、订单 ID、金额、币种。不带「来自 Pyvio」这种字段给业务方（内部日志可以有）。

## 4. 路由规则（聚合的核心）

这是「整合起来」真正要定的产品规则，不是技术细节。

| 场景 | 对外说法 | 对内路由 |
|------|----------|----------|
| 开通银行收款 | 开通收款方式 · 类型=银行 · 币种=USD | Pyvio 开全球账户 |
| 开通链上收款 | 开通收款方式 · 类型=链上 · 币种=USDT · 链=Tron | Actyve 取/绑定地址 |
| 银行入金 | 收款成功 | Pyvio 入账通知 → 记 USD 钱包 |
| 链上入金 | 收款成功 | Actyve 入金通知 → 记 USDT 钱包 |
| 付到银行（USD） | 付款 | Pyvio |
| 付到链上（USDT） | 付款 | Actyve |
| USDT 付到银行 | 付款（或「兑付」） | Actyve BankAccount / GlobalAccount；**需确认** |
| 法币换汇 | 换汇（二期） | Pyvio |
| 稳定币兑 USD | 换汇（二期或跟出金绑在一起） | Actyve 询价 |

**聚合层的价值**：合作方学会一套「客户 / 钱包 / 收款方式 / 付款」，不用分别学两家文档，也不用自己拼 webhook。

## 5. 第一期产品边界（需求口径）

### 5.1 做

1. 商户接入（我们发密钥）  
2. 客户开户与状态  
3. 同一客户下：至少 1 个法币收款方式 + 1 个稳定币收款方式  
4. 分币种钱包余额查询  
5. 入金统一通知  
6. 付款：法币→银行、稳定币→链上（同币种）  
7. 我们自有账本 + 与两通道对账  

### 5.2 明确不做（第一期）

- 虚拟卡、银行卡收银台  
- 人民币结汇材料流  
- 十几个新兴市场小币种全开（先锁 USD + USDT 一条链，例如 Tron）  
- 对外暴露 Pyvio / Actyve 的原始接口  
- 合作方自己选「这笔走哪家通道」（默认由我们路由；高级选项以后再说）

### 5.3 和「BVNK」的关系（需求表述）

对外可以说：**体验上接近「法币虚拟账户 + 稳定币钱包」合在一个 API 里。**  
对内必须说：**不是接入 BVNK，而是用 Pyvio + Actyve 拼出同类能力；托管在通道，我们做聚合与账本。**

## 6. 还必须拍板的 4 件事

不拍板，「聚合」会继续说不清：

1. **资金是否一条线**  
   Actyve 的 `GlobalAccount` 是否就是 Pyvio 全球账户？  
   - 是 → 稳定币可以「进到」法币侧，产品可讲「兑付到银行」  
   - 否 → 对外必须坚持两个钱包，禁止暗示「一个总余额随便花」

2. **谁是 KYC 主路径**  
   客户开户以 Pyvio 为准，Actyve 是否还要单独开户，还是共用主体？

3. **余额以谁为准展示**  
   建议：对外以我们账本为准；通道余额只做对账源。入金以 webhook 终态入账。

4. **商户模式**  
   我们是「大商户自己用」，还是「机构模式」下面挂很多终端客户（对应 Pyvio 的 Unit / 子商户）？  
   这决定客户对象是「我们自己的业务」还是「合作方的每个用户」。  
   **2026-10-03**：商务口头按机构做成，并给提价/分成后台；VA 入账拆成通道费 + 我们分成 + 子商户余额（待书面和沙箱验证，见 [pricing.md](pricing.md) 第 4 节）。

---

## 7. 验收时怎么判断「聚合说清楚了」

下面四句都能对上，需求就算澄清了：

1. 合作方文档里 **不出现** Pyvio、Actyve 作为必接对象。  
2. 同一个客户既能展示银行收款信息，又能展示链上收款地址。  
3. 入金和付款的状态机 **只有一套**，通道差异关在路由里。  
4. 跨稳定币/法币的动作 **有独立产品名**，不会和「查余额」混成一件事。
