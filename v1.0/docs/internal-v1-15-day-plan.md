# Kaloq 内部版 15 天开发排期

> 冲刺计划草案。按 15 个自然日、每天有持续开发投入、现有 Demo 可复用、开发者使用 AI 辅助且业务方每日参加短验收规划。团队人数与实际可投入时间尚未确认，第 1 天核对后调整承诺范围。日期从实际开工日计算。

本排期必须同时执行 [开工准备与开发约束](development-baseline.md)，其中 D1–D3 数据与多服务商设计、D4–D6 适配与执行控制、D9 实例隔离、D11 迁移回滚演练、D13–D14 双实例扩展验收均属于本轮范围。进度不足时压缩界面与开放路径，不推迟上述底座。

实际开工日为 **2026-11-04**。D1 执行及用户最新确认见 [第一天记录](day-01/README.md) 与 [决策登记](day-01/decisions-and-readiness.md)。

## 1. 交付目标

第 15 天交付可供内部员工在独立沙盒环境验收的第一版：运营登录看到全部商户，进入商户办理服务；订单列表与 Pipeline 显示状态、卡点和下一步；资金动作经过冻结、个人审批、签名及执行校验；资金变化可追溯，并能对账及处理异常。

两条方向均作为目标，但真实沙盒闭环依赖通道证据。Pyvio P2A 成功不等于 Actyve 已到账；A2P、链上出款、法币到账分发和银行付款仍须核对最新联调结果。未通过的动作保持关闭，不能用模拟成功宣称闭环完成。

本轮按“核心业务 + 简化管理界面”压缩范围。35 种页面是目标架构，不要求在 15 天内把每个管理页面做成独立、完整的产品。生产放行另需完成生产权限、通道配置、期初账务核定、恢复与资金控制验收；第 15 天不自动等于正式资金业务上线。

## 2. 范围取舍

| 层级 | 本轮安排 |
|---|---|
| 核心操作必须完整 | 商户列表/建档/工作台、资料及目标版本、订单列表/详情/Pipeline、资金申请、本人审批与消息、入金核验、账本与冻结/在途、对账差异、安全告警 |
| 后台控制必须完整 | 数据库事务、商户归属、资金预占、防重复出款/过账、审批个人隔离、签名与最终请求校验、结果未知处理、原子池流水、追加审计、无绕过的执行入口 |
| 管理界面做最小可用 | 员工启停与固定角色；固定审批顺序和具体人员；必要阈值/能力开关；基础任务、回调、告警、恢复申请查询与处理；重要变更有授权与审计 |
| 复用页内组件 | 单笔报价放入订单；异常处理放入订单及差异页；账本和资金流水复用表格/抽屉；后台配置共用设置框架；上述能力不因暂未独立成页而取消 |
| 后续完善 | 全局报价/异常高级工作台、可视化权限编辑器、灵活审批编排、复杂报表、精细仪表盘、批量操作、完整自助恢复体验 |

Google Authenticator、个人签名和受控恢复仍需具备基本闭环。暂不做完整自助恢复页面时，要提供经过授权并留痕的恢复方式，不能靠直接改数据库关闭认证。审批配置先限定已批准的固定规则，不能把“简化”解释为取消财务/主管/EO 节点。

## 3. 每日计划

| 天 | 重点 | 当日可展示成果与完成条件 |
|---|---|---|
| D1 | 定范围、查复用能力、消除依赖 | 确认沙盒 HKD/正式 USD 边界及网络证据，设计角色/审批人、EO 门槛和测试款配置，记录拒绝与释放规则；规划电脑/手机签名；核对最新 Demo 与通道结果；列明两条路径缺口并当天提交给通道方。画商户→订单→审批的低保真原型，评估数据库及部署隔离 |
| D2 | 员工身份与商户入口 | 员工角色、登录/2FA、基本受控恢复；商户列表首页、创建档案、唯一 ID、工作台；运营可见所有商户。验证签名凭证登记技术路径；不能确认的通道动作从可交付承诺中暂时移除 |
| D3 | 业务单与 Pipeline | 主单、阶段、执行子单、资料/报价版本及原始指令落库；商户内订单列表、创建订单、详情与卡点；接现有资料/开户/VA 数据，收款目标绑定商户 |
| D4 | 账务与冻结基础 | 商户分账、池流水序号及前值/收支/后值、事务一致性；本金/费用占用、可用/冻结/在途；提交动作与冻结原子关联。当天覆盖并发超额与重复提交 |
| D5 | 个人审批与通知 | 固定分级审批、节点等待、本人待办/记录、消息及首页提示；接受/拒绝留痕；版本变更重审。两名同角色员工互相看不到审批；提交人与审批人分离规则落地 |
| D6 | 审批签名与执行控制 | 固定快照、个人签名、最终通道请求比对；执行任务可靠落库、幂等、暂停开关、旧 Demo 写入口隔离。修改金额或目标会阻断并生成主管/EO 告警；真实通道写动作只在控制完成后接入 |
| D7 | 法币转数币沙盒路径 | 入金核验→划转/P2A→Actyve 对应到账→测试款（适用）→正式出款；沿用 D4–D6 控制；订单 Pipeline 跟随实际证据推进。通道未确认阶段明确停在等待/未开放 |
| D8 | 数币转法币沙盒路径 | 收 U 与归集→A2P→Pyvio 到账与分发→银行出款；关联来源和目标流水；记录商户到账确认。目标是两个方向都拿到实际沙盒回执 |
| D9 | 回调、补查与异常恢复 | 回调验签、重复/乱序、主动查原单、结果未知、部分成功、任务重启恢复；将真实错误映射为 Pipeline 卡点；完成测试款与主款防重、过期报价和目标变更阻断 |
| D10 | 对账与结单 | 总池/商户归属/通道实账/跨平台在途核对；差异单、授权冲正流程及证据；未决金额和差异阻止结单；本地余额与上游观测值分开展示 |
| D11 | 运维与安全处置闭环 | 监控最低必要指标、告警通知与确认/升级、受控任务恢复、脱敏追踪与追加审计；验证备份和恢复；安全事件关闭不自动解除付款阻断 |
| D12 | 业务走查与范围冻结 | 补商户资料补件、确认凭证、拒绝/重提/撤销、恢复流程、必要配置；由业务方实际办理一笔订单，修正操作不顺与状态不清；当天结束停止扩功能 |
| D13 | 全流程与权限验收 | 按运营、财务、主管、EO、Admin、Root 分别走查；每条开放路径从建档到结单；查角色越权、审批隔离、目标串户、旧入口绕过和通知遗漏 |
| D14 | 故障与安全验收 | 并发、重复/乱序事件、网络超时、部分成功、服务重启、余额差异、审批后改金额/收款方、签名重放/凭证撤销；复测修复点，整理剩余阻断项 |
| D15 | 缓冲、部署及交付 | 只修交付阻断问题；独立测试服务部署、健康接口与登录验证、角色账号和操作说明、已开放/未开放能力清单；业务方完成最终沙盒验收 |

每天开发资金或权限能力时同步完成相应检查，D13–D14 是集中验收，不是第一次测试。中间成果按项目约定同步独立测试服务；D15 是最终交付部署。

## 4. 关键节点与延期处理

- **D2：通道和签名可行性门槛。**拿不到关键接口、权限或回执时，标注依赖人和明确回复期限；继续做无依赖部分，不能把两个方向都算成已确定可交付。
- **D6：执行控制门槛。**冻结、个人审批、签名、最终请求校验和防重没有完成，就不接真实通道写操作；优先推迟非核心管理页面。
- **D8：双向闭环门槛。**若某条路径仍被上游阻断，明确交付“已验证路径 + 受阻路径的界面和状态”，并重新约定受阻路径完成日；不能将该路径宣称已验收。
- **D12：功能冻结。**新需求进入下一轮，不挤占 D13–D15 的验收与修复时间。
- **D15：放行门槛。**存在可能错付、重复付款、串户、越权审批或不可追溯账务的问题时，受影响动作保持关闭；以实际验证范围交付。

进度落后时，先压缩界面独立拆分、视觉精修、高级查询与报表；再减少开放资产/网络和业务动作。不能通过取消签名校验、审批、冻结、对账或故障验证来维持表面工期。

## 5. 协作方式与工作量边界

建议每天安排一次短验收，业务方确认当天流程和待定规则；开发方维护已完成、受阻、次日目标三项记录。通道疑问在 D1 集中提出，后续每天跟进，不能等页面完成后才开始联调。

若实际只有一名开发者加 AI，以上为压缩范围后的冲刺目标，D1 需以现有代码复用程度重新估算；若 15 个自然日中包含休息或兼职投入，需要减少范围或延长时间。若有两名开发者，可分别负责业务页面/权限与账务/执行集成，但共同评审数据契约及资金控制，不能把团队人数直接当作工期按比例缩短的依据。

本轮优先确保运营能完成真实业务路径，管理页面随后完善。依赖全部如期解决，也不能以“35 页都能打开”代替闭环验收。
