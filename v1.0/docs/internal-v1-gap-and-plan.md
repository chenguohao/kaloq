## 1. 第一版定位

在现有 API Demo 上建立可供内部人员使用的业务后台，复用已经联调的通道能力，补齐商户归属、业务订单、运营提交、分级审批、资金占用、执行、到账核验与对账结单。

第一版采用固定角色和固定审批顺序，不做通用拖拽流程引擎。客户为商户；操作员为运营；审批包括财务、主管、EO；系统维护包括 Admin、Root。角色定义见 [内部版需求](internal-operations-requirements.md)。

功能拆解只列平台实际承担的操作。建群、拉人、线下人员分工及需求沟通属于系统外业务过程，不据此增加服务群管理、商户负责人分配或需求登记功能。商户模块从平台注册、信息录入及唯一商户 ID 生成开始；业务订单经办人、审批人和异常处理人仍属于实际的平台权限与流程记录。

## 4. 审批机制（等待、通知、办理和留痕已确认）

### 4.1 审批对象与顺序（顺序仍为建议方案）

资料审核与资金审批分开：商户资料/收款目标由财务核对；报价由运营登记并经主管确认；资金申请按“运营提交 → 财务 → 主管 → EO（达到门槛时）→ 系统执行”。

按每次将要执行的动作审批：划转/P2A、A2P、链上付款、银行付款和测试付款均关联明确指令。第一版建议把“子账户划至主账户 + P2A”作为一组审批动作，其下保留两笔执行单；第二步失败不能把第一步已转走的资金当作仍在子账户。是否合并这两个动作仍需确认。

### 4.2 每个人实际看什么

| 人员 | 界面内容与动作 |
|---|---|
| 运营 | 选商户和业务单、选已确认目标、填金额、报价和费用、上传原始指令，查看可用与占用金额，提交后只读 |
| 财务 | 对照原始指令、实际入金、客户归属、账本、金额和费用；接受或拒绝，并记录意见 |
| 主管 | 审查财务结论、报价、业务条件、付款目标及测试要求；接受或拒绝 |
| EO | 对达到门槛的申请做最终审批；显示金额、费用、目标和前置审批条件是否满足，不展示其他人的专属审批记录 |
| 系统 | 全部审批完成后生成执行任务，执行前再次检查条件；不让审批按钮直接同步调用供应商付款 |

### 4.3 流程等待、通知与办理（已确认）

1. 流程到达审批节点时，进入“等待审批”，记录本节点指定审批人；本节点未获接受前，不执行依赖它的后续步骤。
2. 为指定审批人创建审批待办，并在其消息中心产生一条审批消息。审批人登录后，首页显示待审批提示；登录之前已产生的待办也必须展示。
3. 从消息中心或首页提示点击进入对应审批页，查看本笔流程的相关内容，并可选择“接受”或“拒绝”。
4. 接受后，系统保存审批结果并推进流程；下一步仍是审批节点时，进入下一位指定审批人的等待节点，并发送对应消息。全部必要审批完成后才进入后续执行。
5. 拒绝必须保存审批记录，不得当作通过继续原执行路径。拒绝后终止还是退回哪个节点、是否可修改后重新提交，待业务确认；下节原有终止/释放方案仅为建议。
6. 每次审批均留痕，至少记录流程/订单编号、申请版本、审批节点、指定审批人、实际操作人、结果、意见和审批时间；审批记录按个人专属权限查看，不因同属一个角色或团队而共享。
7. 审批是个人专属：每个人只能查看和处理明确分配给自己的审批，包括待审批、已审批、审批详情和个人审批记录；看不到其他人的审批。消息中心、首页提示、待办数量、搜索和导出均按本人隔离。财务、主管、EO 同角色人员之间不共享审批；Admin、Root 也不因维护身份默认获得查看他人审批的权限。后续审批人可查看本节点所需业务资料和前置条件是否满足，不因此获得其他人的审批详情、意见或记录。
8. 新增已确认：审批人使用自己的密钥签署固定的资金指令快照；系统在执行前验证各级签名，并核对最终发往 Pyvio/Actyve 的业务参数。出现不一致拒绝执行并通知主管及 EO。个人签名与 Google Authenticator 动态码分开；签名载体建议及安全告警的独立权限见 V17 详细方案。

### 4.4 实现与验收补充（建议）

- 消息“已读”与待办“已处理”分开；阅读通知不能完成审批。已处理后首页待办数更新，原消息仍可查看结果。
- 审批页展示商户、业务类型、金额、币种、报价及费用、收款目标、原始指令与附件、此前业务步骤和本人审批记录，按本节点职责展示核验内容；其他审批节点仅提供前置条件是否满足，不展示他人的审批详情或意见。
- 同一节点、同一申请版本只建立一条有效待办；服务端按当前登录用户与指定审批人校验列表、详情、消息、附件访问、审批动作和导出权限。不能通过修改 URL、猜测 ID 或直接调用 API 查看或处理他人的审批；前端隐藏入口不能代替服务端隔离。
- 审批结果、记录、待办完成和流程推进在数据库事务中处理；后续消息/执行任务可靠入队，失败可重试，不能丢待办或跳过节点。
- 重复点击、并发提交、刷新与服务重启不得产生重复审批、重复通知或重复执行；已处理页面只展示结果，不再允许操作。
- 拒绝建议填写原因；意见是否必填、转交/替岗权限及提醒时限待确认。个人专属已确定，不提供团队公共审批池；转交机制确认前不得开放代看、代审。
- 验收至少使用两名同角色审批人交叉测试：列表、搜索、数量、通知、详情、附件、审批动作和导出都不能泄露另一人的审批。串行审批的后续节点也不得借流程详情查看前一审批人的专属记录。

### 4.5 其他待确认规则

- 提交时固定申请版本、收款资料版本、报价、金额、费用和审批路线；审批意见只对该版本有效。
- 不允许自审；同一人员不能在同一申请上充当多个必需审批人。替岗只能由有该权限的其他人员接手并留痕。
- 已确认流程指派到具体审批人；建议第一版每级指定一人，不做多人会签。各节点如何从财务、主管、EO 中指定人员及替岗规则待确认。
- 退回、拒绝、执行前撤销均终止本版本并释放可释放占用；修改后以新版本重新提交，走完整审批，不继承旧通过结果。
- 提交执行后不能仅点击撤销就释放资金；须确认供应商撤销/失败及资金可恢复。
- 报价过期进入待重新报价，不自动按新价格执行。重新报价及客户确认后重新提交；旧占用不得和新申请重复计算。
- 审批后关键字段变化，必须重新审批；审批策略变更不得使历史申请自动跳过原有审批，紧急收紧时可暂停未执行单。
- 审批通过不代表执行成功；执行前仍检查客户状态、目标状态、报价、资金及暂停开关。
- 无合格审批人时保持待审批；不自动降级或默认通过。通知和待办至少在站内提供。

## 5. 冻结怎么冻结（建议默认方案）

### 5.1 冻结的含义

第一版的冻结是 Kaloq 内部账本按商户、订单和币种预占资金，防止同一笔余额被多张申请重复使用。除非供应商提供并实测了冻结接口，不能称为 Pyvio/Actyve 已冻结。

这个约束只覆盖经过 Kaloq 的资金动作。直接从供应商后台或其他系统动用余额，仍会导致账实差异；执行前须查实际可用额并阻断差异，不将内部冻结当作上游资金保证。

### 5.2 时点和金额

草稿不冻结；提交资金申请时，在一个数据库事务中完成余额校验、订单版本保存、冻结和首级审批待办。失败则整体回滚，不能出现已提交但未冻结。

冻结金额 = 本次来源本金 + 同一来源币种的费用预留。目标到账模式必须按报价反算来源扣款。费用币种不同则单独预占对应币种，不把 USD 和 USDT 相加。不用浮点数进行资金计算。

例如可用 1,000 USD，申请本金 600 USD、费用 10 USD，提交后可用 390、冻结 610；另一张申请不能再次使用这 610。明确失败或执行前终止后，可释放 610；成功按实际扣款核销。该例仅解释账务，不代表通道费率。

### 5.3 资金生命周期

| 事件 | 账务处理 |
|---|---|
| 提交申请 | 可用减少，审批冻结增加；写入独立冻结记录 |
| 审批通过、尚未提交上游 | 保持占用，等待任务执行 |
| 上游受理、资金正在跨平台移动 | 记录来源扣款/占用与在途归属；同一资金不能同时计入可用和在途 |
| 结果未知或超时 | 保留相关占用或在途，查询原订单，不自动解冻或再付 |
| 执行前退回/拒绝/撤销 | 释放该申请未执行部分，不释放其他订单占用 |
| 上游明确失败 | 核实未扣款或已退回后释放；已产生的费用按实际核销 |
| 来源已扣、目标未到账 | 保留在途，不能按全单失败恢复来源可用 |
| 目标到账确认 | 依据关联证据把在途转为目标阶段资金；不同币种分别过账 |
| 实际费用小于预留 | 核销实际费用，释放未用差额 |
| 费用超预留、金额或条件变化 | 停止执行、更新报价和申请，补充占用并重新审批；不能自动超扣 |

### 5.4 多阶段如何衔接

法转数：商户 USD 预占 → 划转/P2A 在途 → 核验 Actyve 对应到账及兑换 → 保留商户归属的待付款金额 → 付款冻结 → 链上付款核销。

数转法：核验收 U 及可兑换状态 → A2P 预占 → A2P 在途 → Pyvio 主账户到账 → 分发在途 → 子账户 USD 确认可用 → 银行付款冻结 → 付款核销。

主池资金按业务单和商户记录归属，不能因为处在公共账户就成为其他商户可用余额。商户归属的数币过渡资金是内部记录，不新增商户长期数币钱包。

第一阶段结束后，以实际目标到账建立下一阶段占用关系；同一笔资金只在一个有效阶段占用。测试付款独立列账，计入总额时主付款扣除已测试部分；不计入时须有额外授权和余额。

### 5.5 工程验收

必须覆盖并发提交不能超额、重复点击不重复冻结、重复/乱序回调不重复过账、任务重启不重复付款、明确失败与结果未知不同处理、部分成功不全额释放。每次占用、释放、核销都关联原单并保留分录，不能通过改余额数字代替。

新增总池记账必须同时满足：同池同资产序号及前后值连续、商户分账与池账事务一致、上游实账独立核对。该本地原子记账不代表跨 Pyvio/Actyve 调用具有分布式原子性，详情见 V16 方案。

## 9. 双因素认证（2FA）

### 9.1 选型与费用

已确认：第一版使用 Google Authenticator，采用标准 TOTP：密码通过后，再输入 Google Authenticator 生成的 6 位动态码。Kaloq 后端生成绑定密钥并自行校验，无需购买第三方身份认证服务，没有短信费或按次验证码服务费；开发、服务器和维护仍有成本。

绑定页面和使用指引统一采用 Google Authenticator。Google 官方说明支持其他网站/应用、离线生成及不登录 Google 账号使用。Kaloq 使用标准 TOTP 在本地服务端校验，不需要接入 Google 登录、企业 SSO 或推送审批。

后端可评估 Go 开源库 `github.com/pquerna/otp`（Apache-2.0，支持 TOTP 和绑定二维码），开发时检查版本、依赖及漏洞后固定版本。本次未安装依赖或实现功能。

参考：[TOTP 标准 RFC 6238](https://www.rfc-editor.org/info/rfc6238/)、[Google Authenticator 官方说明](https://support.google.com/accounts/answer/1066447)、[Go OTP 库及许可证](https://github.com/pquerna/otp)。核查日期：2026-10-31。

### 9.2 使用范围（建议默认规则）

- 运营、财务、主管、EO、Admin、Root 强制绑定。首次使用或被重置后，只能进入绑定流程，绑定完成前不能访问业务功能。本轮商户不创建登录账号；认证器绑定仅面向内部员工（2026-11-04 按已确认内部版范围纠正）。
- 登录：密码验证后仅发短期、受限的 2FA 挑战；验证码通过后才建立完整登录会话。不能用密码登录接口或旧 Demo 入口绕过。
- 敏感操作：财务/主管/EO 的资金审批通过、存在人工执行时的付款确认、收款目标生效或变更、员工权限变更、2FA 解绑及重置，需要再次验证。
- 敏感操作挑战绑定用户、会话、动作、订单/资料版本，建议有效期 5 分钟且仅可消费一次。验证完成与动作提交原子衔接；变更金额或目标后不可复用。时间窗口、失败次数等是待确认默认值。
- 后台自动任务不要求人工重复输入验证码，但只执行审批完成的固定版本指令。2FA 不代替财务/主管/EO 的审批权限。

### 9.3 绑定、恢复与防重放

1. 绑定时展示 Kaloq 名称、用户标识、二维码及手动密钥；密钥只在受限绑定流程中展示，不通过第三方在线二维码服务生成。用户输入首个有效验证码后才启用。
2. 默认采用兼容常用认证器的 6 位、30 秒 TOTP，允许前后一个时间步偏差；服务器保持时间同步。每个用户记录已消费时间步，同一码不能反复用于登录或审批；验证和消费必须防并发重放。
3. 绑定后生成一次性恢复码，只展示一次，服务器仅存哈希。恢复码用于受限恢复流程，不能直接代替交易审批的再次验证；恢复后须重新绑定。
4. 正常换机/解绑需密码与当前 2FA。遗失设备且无恢复码时走人工身份核验和受控重置，不允许仅凭邮箱或普通密码取消 2FA。
5. 建议 Admin 可发起普通员工重置、Root 确认；Root 自身遗失时使用独立受控恢复流程，不能自批重置。重置授权人、身份核验材料及紧急恢复保管方式待确认，启用强制 2FA 前必须落实。
6. 重置后撤销原密钥、恢复码、登录会话和敏感操作挑战，要求重新绑定；记录原因、操作者、审批者及时间，通知账号本人。管理员不可查看现有 TOTP 密钥。
7. 验证接口按账号及 IP 限流，建议挑战 5 分钟有效、连续失败 5 次使挑战失效并触发冷却，不能无限尝试 6 位码。日志不得记录动态码、绑定密钥、二维码内容或恢复码。
8. TOTP 密钥加密保存，解密密钥与数据库及 Web 根目录分离；它需要用于计算校验，不能像密码一样仅存哈希。恢复码则仅存哈希。

### 9.4 页面与验收

新增绑定页、登录验证码页、个人安全设置、恢复码保存/重新生成、敏感操作验证框、员工绑定状态和重置申请入口。

验证：未完成 2FA 无业务会话；无验证码不能完成受保护操作；错码/过期码被拒绝；并发提交同一码最多成功一次；恢复码不可重复使用；重置撤销旧会话和旧密钥；旧 API 与 Demo 写入口无绕过；密码重置不移除 2FA。

TOTP 仍可能被实时钓鱼，也不能用于签署订单快照。新增 V17 将审批人个人签名纳入第一版需求，建议采用 WebAuthn 凭证或安全密钥，载体待确认；Google Authenticator 的已有身份验证用途保留。
