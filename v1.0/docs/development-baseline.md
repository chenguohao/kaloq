## 1. 必须达到的结果

新增提供已有业务能力的服务商，应主要增加适配代码、实例配置、账户绑定与联调用例；不得要求重整存量商户、改写历史订单、重算历史账本或停用现有通道。新增通道可独立开放、暂停和退出；历史订单仍可查单、接收回调、对账及结案。

这不是“永远不改数据库”或未经验证的零中断承诺。允许兼容的新增表、索引和可选字段；真正的新产品可能需要模型演进，但必须另行评估兼容性和发布方式。不得以 15 天工期为由推迟下述基础边界；可以减少页面和开放路径。

当前代码只是起点：Core 为单 Provider，统一 Pyvio Adapter 为占位，真实调用主要在 sandbox 模块。不能把通用架构提案当作已实现，也不能直接复制 Demo 的供应商分支作为正式执行架构。

## 3. 数据模型必须提前留出的边界

以下是逻辑关系要求，表名可调整，D1–D3 必须形成可评审 schema、索引和约束；不要求照搬表名。

- 平台 merchant/customer 使用稳定 ID，独立于供应商客户号。通道开户、资格、补件状态按商户和服务商实例单独记录，一家通过不代表其他家通过。
- provider_instance 区分品牌、签约账号、环境；只保存凭证引用、能力配置版本和审计，私钥独立存放。支持同时注册多实例，不靠全局单一 Provider 开关替换运行中的通道。
- provider_binding 保存商户、平台账户、受益人/收款方式与外部资源的关联。外部 ID 的唯一范围包含实例、资源类型及供应商要求的账户范围，不能假设外部单号全局唯一。
- 平台账户与通道资金位置分开。余额按商户、资产、网络（适用）、资金位置及可用/冻结/在途区分；跨位置调拨是显式步骤，不能用总余额证明某通道可出款。金额用精确整数或定点数，接口用十进制字符串，禁止浮点计算。
- 主订单关联多个执行步骤。每步固定 provider_instance、来源/目标绑定、资金位置、资产金额、长期请求号、外部单号、状态和尝试记录；保存路由/报价/审批快照及版本。任务恢复和查单使用该步骤绑定，不能读取当前默认通道重新路由。
- 资料、目标、报价、审批路线和签名载荷版本化；修改关键字段形成新版本并重新审批。审批签名覆盖执行相关的实例、账户和路由；已签版本不可静默换通道。
- 专有字段放独立扩展表或有 schema_version 的 JSON，适配层验证及映射。金额、归属、执行状态、关联键和去重键必须有明确结构与约束。不得不断向商户主表添加 pyvio_xxx、vendorB_xxx 字段。
- 回调 Inbox、外部流水去重、账务过账唯一键必须包含实例和适用资源范围。事件去重与资金动作去重分别实现；同笔到账不同事件 ID 不能重复过账。链上标识包含网络、资产和必要事件索引。
- 账本追加记录、同币种平衡、占用与过账原子关联；纠错通过授权冲正，不覆盖历史。所有时间以 UTC 保存，展示时转换。

## 4. 代码、执行与故障边界

1. 按开户、收款、报价/兑换、付款、查单等能力定义小接口；实例注册声明已验证的资产、网络、目标类型、限制和环境。首期允许固定路由配置，不要求自动择优或智能切换。
2. 供应商 SDK、鉴权、字段、错误码和状态映射留在适配层；业务层统一决定状态推进与记账。前端调用平台 API，供应商额外补件通过受控要求模型表达，不污染所有客户的必填字段。
3. 正式资金动作统一经过归属、占用、个人审批、签名和最终请求校验。旧 Demo、API 凭证、后台任务都不得绕过；接口直接调用供应商的试验代码不得成为正式执行入口。
4. 提交超时、任务崩溃或结果未知，保留占用并向原实例查单；不能自动换通道或换请求号重付。部分成功只处理确认部分，不全额释放。供应商观察结果不能直接覆盖平台余额。
5. 按实例设置超时、并发/限流、重试上限、任务领取配额及暂停策略，避免一家故障耗尽全部任务和连接资源。暂停新提交与保留查单/回调/对账分开控制；撤销凭证前核清存量订单。
6. 公共 API、事件及任务载荷版本化，兼容已经创建的任务和历史事件。新增服务商不要求老客户端增加专有字段。附件、查询、导出、通知及审批数量均执行服务端权限隔离。
7. 监控至少按实例区分错误、未知结果、回调积压、任务重试、在途和账实差异，保留商户→订单→步骤→通道单→账务的脱敏追踪。

## 5. 数据库演进和发布规则

- 上线前确定迁移工具、版本记录和唯一执行者，禁止多个进程并发迁移；迁移脚本纳入版本管理，不手工改线上业务数据。
- 采用“先扩展、再切换、最后收缩”：先加兼容结构，发布兼容新旧读写的代码；确有需要时分批、可续跑、可核对地回填，验证后切换。删除旧字段、改名、改变类型或语义必须在后续独立变更中处理。
- 迁移前用接近实际规模的数据评估锁、扫描和执行时间，设置锁/语句超时；索引等可能阻塞写入的操作须选择适当执行方式。不能把“大表一次 UPDATE”当作无影响变更。
- 发布说明列出旧版本兼容性、在途任务兼容性、迁移步骤、备份、恢复验证、回滚条件和停止条件。新代码失败时能回到兼容旧结构的应用版本；不盲目逆向迁移或用旧备份覆盖发布后已产生的资金记录。
- 新服务商默认关闭，先测试实例与指定测试商户，再逐步开放。新接入与既有服务商切换、账户迁移、收款信息换发、存量资金转移分别实施；新增服务商不自动迁移任何现有账户。
- 生产首次建库也要有可重复的版本化脚本。本轮如需迁移 Demo 的 JSON 状态，先区分测试数据与应保留证据，试迁移并核对映射，禁止未经确认清库；完成后正式订单不再以 Demo JSON 作为唯一状态来源。
- 本项目继续使用独立 kaloq-demo 服务、数据库和端口，按 AGENTS.md 部署；文档修改无需发布运行服务。应用或配置变更执行相关检查后部署，并验证健康接口和登录。单实例服务目前不能据此宣称无中断滚动发布；生产如要求不中断，须验证多实例、共享会话/任务协调与流量切换后再承诺。

## 6. 开发检查和验收门槛

每次涉及数据、执行或通道的变更，提交说明必须列出：适用约束、数据库/API/任务兼容性、存量订单影响、开关与回滚、实际验证结果。未验证项明确标注，不能写“应该兼容”作为通过证据。

| 节点 | 必须留下的证据 |
|---|---|
| D1–D3 设计门槛 | 决策登记；schema/唯一键；状态机；多实例绑定；路由和签名快照；迁移策略。未评审前不固化正式资金表和执行流程 |
| D4–D6 实现门槛 | 真实通道收口到适配层；冻结/审批/签名/执行校验；按原实例恢复；去重和事务验证；无旧入口绕过 |
| D9 集成检查 | 重复/乱序回调、相同外部 ID 出现在不同实例、同实例不同账户、超时和重启，不串单不重复付款/过账 |
| D11 发布检查 | 增量迁移演练、旧应用兼容、回滚及备份恢复证据，保留发布后资金记录的恢复方案 |
| D13–D14 扩展验收 | 同一进程注册 A/B 两个测试适配器或实例；A 存在处理中/未知订单时新增 B，全程验证 A 的提交、查单、回调和记账；B 超时/错误/积压/停用不耗尽 A 的处理能力；修改默认配置后 A 旧单仍查 A；重启后同样成立 |
| D15 放行 | 已开放/关闭清单、剩余依赖、迁移和回滚记录、权限/资金/扩展隔离验收证据；缺少关键证据不得宣称可生产上线 |

扩展验收中的测试适配器只证明架构隔离，不能代替新供应商的真实联调。正式新增供应商仍须完成其账户资格、资金路径、费用、回调、幂等和对账验证。
