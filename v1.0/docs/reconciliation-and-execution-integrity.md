# 总池对账、审批签名与监控告警

> 2026-11-04 范围更新：沙盒 HKD 样例、正式 USD；角色人员、EO 门槛和测试款采用可更新配置；个人签名支持电脑和手机；平台收费留待单独需求。通道实际扣款、到账及扣费随回执记录核对。详见 [D1 确认与决策登记](day-01/decisions-and-readiness.md)，本说明优先于下文相冲突的旧建议。

> 2026-10-31。新增第一版需求。用户已明确要求逐笔原子流水、个人密钥签署审批快照、执行前比对以及异常拒绝和告警；本文中的数据模型、签名载体、阈值和实现流程为开发方案，尚未实现。

## 1. 范围与原则

增加两个独立模块：**总池账本与对账**、**监控与防篡改**。覆盖 P2A、A2P、商户与主账户之间的划转、数币及银行出款、费用、退款和调账。不能只在最后结单时检查总余额。

总池多人共用，但每笔资金必须明确商户归属；每笔记账能还原前值、收支和后值；审批人批准的指令必须与实际送往通道的业务指令一致。对账查询和安全告警有独立权限，不扩大“个人专属审批”的可见范围。

## 2. 每笔资金池变动记录

| 字段组 | 必需内容 |
|---|---|
| 唯一身份 | 流水 ID、资金池 ID、池内递增序号、幂等事件键 |
| 通道及资产 | Pyvio/Actyve、实际账户或地址标识、币种、网络（适用时）、余额口径 |
| 时间 | 上游业务发生时间、系统接收时间、数据库记账时间；统一保存时区，界面按用户时区展示 |
| 业务归属 | 商户 ID、主订单、执行子单、资金阶段、上游订单/流水 ID、链上交易 ID（适用时） |
| 人员与执行身份 | 发起操作的员工、实际执行的服务/任务身份、触发来源、执行尝试 ID；自动入金记录通道来源，不伪造员工操作 |
| 变动 | 变动前账面余额、收入或支出及金额、费用分录关联、变动后账面余额 |
| 关联证据 | 对应商户分账分录、冻结/在途记录、已签审批快照哈希、请求及回执摘要、追踪 ID |
| 审计 | 记录版本、前序记录摘要、本条摘要、更正原因及冲正引用（适用时） |

同一池、同一资产、同一余额口径内：**后值 = 前值 + 收入 − 支出**。金额使用整数最小单位，跨币种不相加抵销；同名代币在不同网络的实际头寸分别记录，需要汇总时明确换算/汇总口径。

示例仅解释账务，单位为 USD：

| 序号 | 商户 | 操作 | 前值 | 收入 | 支出 | 后值 |
|---|---|---|---:|---:|---:|---:|
| 101 | 商户 A | 子账户划入主池 | 10,000 | 1,000 | 0 | 11,000 |
| 102 | 商户 B | 子账户划入主池 | 11,000 | 2,000 | 0 | 13,000 |
| 103 | 商户 A | P2A 来源本金扣款 | 13,000 | 0 | 600 | 12,400 |
| 104 | 商户 A | 本笔手续费 | 12,400 | 0 | 10 | 12,390 |

本金与费用可在同一个数据库事务中各写一条分录。必须能追溯到同一执行子单；商户 B 的资金不因商户 A 的付款被挪用。

### 2.1 原子性与并发

在一个数据库事务中完成：校验/锁定池余额版本 → 校验商户可使用头寸 → 写池流水 → 更新池余额 → 写商户分账和复式分录 → 更新冻结或在途及订单阶段 → 写可靠事件。任一步失败整体回滚。

采用数据库行锁或等价的并发控制，同一池的分录有唯一序号和连续前后值；涉及多个账户时按固定顺序加锁。重复回调、重复查单及重试通过唯一事件键去重，不能重复记账。单进程互斥锁不能代替数据库约束。

**原子性只承诺 Kaloq 内部一次记账的完整性。**数据库提交与 Pyvio/Actyve 请求不能组成同一个本地事务；执行指令先可靠落库，再由任务发送，凭实际回执/查单/回调推进结果。崩溃或超时留在待核实状态，不自动假定成功、失败或退款。

### 2.2 本地账面余额与通道实际余额

- 前值/后值由本地连续账本确定；上游余额另保存为带查询时间的观测值。两者不能混为一个“实时余额”。
- 上游查询前后可能穿插其他商户的入金、扣费或后台操作，不能把两次查询差值直接归因到当前订单。
- 冻结只是本地资金用途占用，不等于总池已对外付款；冻结不再扣一次池实际余额。在途按来源扣款和目标入账分阶段记录，不能在两边重复算可用。
- 实际池的账户、网络及余额口径以通道核实结果为准。尚未证明 Actyve 存在统一可查询的总池余额时，不将各地址余额冒充该余额；记录各实际账户头寸及归集在途。
- 上线启用账本前按实际通道记录和商户归属核定期初余额；历史无法归属的部分放入待核实项，不能靠补零或调整到“平账”。

## 3. 对账体系

| 对账层级 | 核对对象 | 发现的典型问题 |
|---|---|---|
| 单笔订单 | 审批快照、执行指令、通道订单、费用、实际到账 | 金额或目标变化、重复付款、漏记费用、部分成功 |
| 总池 | 池内账本与同口径上游流水/余额 | 漏入账、重复入账、外部后台操作、余额缺口 |
| 商户归属 | 池内各商户分账及平台自有/待认领头寸与池账本 | 串户、无归属资金、主池金额已分配但商户仍显示可用 |
| 跨平台 | P2A/A2P 来源扣款、在途、目标到账及兑换关系 | 只见扣款不见到账、跨平台流水关联错误 |
| 结单 | 本单全部入出款、费用、退差、剩余、冻结及在途 | 未决资金被提前结单、剩余未处理 |

同资产、同地点的归属分账之和，应等于对应池账面头寸；平台自有、待认领与费用归属必须明确。跨平台在途另列，不能混入两边可用余额凑平。

支持事件触发核验和定期批量对账；定期周期、日切时间、在途超时阈值及经验证的舍入容差另行配置。无法归属、少款、多款、手续费差异和通道外变动自动形成差异单，指派处理并保留证据。未知来源先挂待认领，不自动分给某商户。

更正只能以关联原记录的冲正/补充分录完成，经过授权审核；禁止覆盖余额、删除历史流水或修改原分录来平账。对账差异未经解决不得结单；是否暂停整池按差异范围和严重度配置。

## 4. 审批快照

快照是在提交审批时固定的资金指令版本。审批页展示该快照，审批人签署的也是同一快照。不能仅签“订单号、金额、地址”三个字段，因为币种、链、费用、资金来源变化也会改变付款含义。

| 类别 | 纳入快照的关键内容 |
|---|---|
| 身份及动作 | 快照格式版本、环境、商户 ID、订单 ID、执行子单、订单版本、操作类型、通道 |
| 资金来源 | 来源池/Unit/账户、来源资产及网络、来源扣款金额 |
| 付款结果 | 目标币种及网络、目标到账金额、收款人身份、完整银行账户或链上地址、Tag/Memo |
| 收款资料 | 通道 payee ID（适用时）、对应完整目标详情、资料版本及核验依据；不能只签一个可被重新指向的 ID |
| 价格及费用 | 报价 ID/版本、有效期、计价方向、费用币种和承担方、已确认费用或明确授权上限 |
| 关联条件 | 测试单、是否计入总额、审批策略版本、执行指令编号；合并动作的每个执行子单均在签署范围内 |

建议用标准化 JSON（如 JCS）计算 SHA-256，金额作为最小单位整数字符串，防浮点及大整数精度损失；地址按链的规则处理，不做通用小写化。完整快照、哈希算法和规范化版本都保留。JCS 对可重复序列化及高精度数值的处理见 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)。

业务关键字段改变必须创建新版本、重新展示和审批。若费用允许范围或某些条件可变化，允许范围本身也必须签入快照；默认不允许自动扩大金额或更换目标。

## 5. 审批人签名

**已确认要求：使用审批人自己的密钥签名。**建议通过 WebAuthn 凭证/安全密钥实现，审批人在设备上确认，系统保存个人公钥和凭证 ID，不托管可供后台冒签的个人私钥。同步型 Passkey 与设备绑定/硬件密钥的选型待确认；若要求不可导出和严格设备约束，需选可验证该属性的凭证方案，不能假设所有 Passkey 都满足。

Google Authenticator 继续承担已有登录/二次验证用途。TOTP 是基于共享密钥的动态码，不能替代审批人的非对称签名；不能用验证码或服务端持有的 TOTP 密钥冒充个人签名。依据：[RFC 6238](https://www.rfc-editor.org/info/rfc6238/)、[W3C WebAuthn](https://www.w3.org/TR/webauthn-3/)。

建议的签名流程：

1. 审批页加载并展示固定快照。客户端从展示所依据的同一份结构化数据重新规范化、计算摘要，避免显示对象与签名对象分离。
2. 为本次审批生成一次性安全随机 nonce，构造绑定快照哈希、审批节点、审批人、接受/拒绝决定、有效期、环境及用途的签名上下文。
3. 若选 WebAuthn，使用包含随机 nonce 和该上下文承诺的 challenge（例如二者确定性组合后的摘要），不是只使用长期不变的订单哈希；认证器对包含 challenge 的 WebAuthn assertion 数据签名。保存 nonce、上下文、clientDataJSON、authenticatorData、signature、credential ID，便于以后独立复核关联。
4. 服务端按 WebAuthn 标准校验签名、challenge、RP ID、origin、用户在场及验证标志，并检查凭证属于本节点指定审批人、未被撤销、角色和审批状态有效。认证器计数器作为辅助信号，不将同步凭证的计数器行为简单当作篡改结论。
5. 事务内消费一次性挑战，保存签名和结果并推进节点。同一订单各必需审批节点分别签署同一快照哈希；签名不同，签署的业务版本一致。

凭证登记、增加、撤销和重置必须有受控身份核验和审计，不能用“管理员换一个公钥”伪装原审批人。历史公钥及版本保留供历史验签；被撤销或疑似泄露凭证所签的未执行申请暂停复核。密钥重绑不会使旧待执行申请自动通过。

个人专属审批保持不变：员工只查看自己的审批待办及记录，系统执行服务可以验全部必要签名。主管/EO 通过安全事件权限查看该事件必要证据，不获得其他人的日常审批列表访问权。

## 6. 执行前防篡改

校验范围必须覆盖**实际将要发出的通道指令**，不能只重算数据库订单而不检查接口参数。

1. 加载已审批快照及所有必要签名，核验签名、节点、人员、版本、凭证状态和执行资格。
2. 从固定快照构造执行指令。重算当前订单关键字段摘要，确认其与已签快照一致；金额、币种、网络、完整目标、来源账户或授权费用条件不符，进入安全阻断。
3. 通道适配器生成最终请求后，按预先定义的映射校验其资金字段及请求头中的来源 Unit 与已签执行子单一致。若请求只传 payee ID，还需核对该 ID 解析出的目标与已签目标资料一致；上游可变资料无法固定或核验时应阻断并列为接入缺口。
4. 固定最终请求的业务内容、保存请求摘要和执行尝试 ID。时间戳、令牌、供应商请求签名等传输字段允许按协议更新，不参与业务快照的等值比较；生成这些字段后不能再更换资金字段。
5. 以数据库版本条件原子地标记该指令进入执行并可靠入队。执行服务在发出调用前仍检查受控暂停及撤销条件，使用同一个不可变指令生成请求；其他进程修改订单必须导致版本冲突或重新审批。
6. 出现差异、缺少签名、验签失败、越权或重放：**拒绝调用通道，保存证据，生成安全事件并通知主管及 EO**。数据库或审计存储故障时不继续付款；告警投递异常要进入独立监控，不能因投递失败放行。
7. 已发送请求后才发现问题时，标明“已提交/结果待核实”，立即阻断后续动作、查询原单并按可用能力处理，不能声称已阻止该笔资金转出；禁止自动重付或解冻。

已签快照中的业务授权不等于执行时的可用余额保证。执行前还需核验当前余额、冻结、报价有效期和通道状态。每次已发生的资金变动再按第 2 节进入原子流水。

## 7. 监控与告警

| 监控面 | 主要检查 |
|---|---|
| 业务追踪 | 一笔业务串联申请、审批、冻结、执行任务、请求/回执、回调、池流水、商户分账、对账和告警；按订单/执行/追踪 ID 查询 |
| 运行状态 | 接口错误和延迟、鉴权失败、任务重试/积压、回调投递/验签失败、数据库错误、日志或监控停止上报 |
| 资金状态 | 前后值断链、池账与上游差异、跨商户归属异常、重复记账、长时间冻结/在途、未认领资金 |
| 员工与配置 | 审批后修改关键字段、异常权限提升、公钥替换、未经授权的人工调账、绕过执行入口及通道配置变更 |
| 执行安全 | 快照不符、验签失败、凭证被撤销、审批缺失、幂等指令重放、最终请求目标被替换 |

金额/收款目标不符及签名异常按最高级别安全事件处理，立即阻断相关执行。告警先进入主管、EO 的消息中心及首页安全待办；Admin/Root 接收适合其职责的运维事件，业务敏感证据按独立授权展示。告警发给哪些具体人员、是否还需离线触达、重试及升级时限待配置；站内消息不能承诺让未登录人员即时知晓。

告警包含事件编号、发现时间、订单与商户、执行阶段、期望快照摘要、实际请求摘要、字段差异、发起/执行身份和证据引用。默认脱敏，授权调查才查看完整目标信息；日志不输出认证秘密和私钥。

告警状态：新建 → 已通知 → 已确认 → 处理中 → 已解决/误报；相同事件聚合防刷屏，但不覆盖新证据。失败投递可靠重试，超时升级。关闭告警不能自动解锁付款，修复后按规则重新审批或重新核验。

## 8. 审计证据与保护边界

单纯把快照和哈希放在同一可修改数据库里不足以防篡改：攻击者可同时改二者。个人签名用于验证原审批内容，池流水采用只追加、前后序号及摘要链；审批签名、凭证登记历史和审计摘要另行写入独立权限的追加存储或定期外部留存，发现整段重写或删除。

摘要链也不是绝对不可修改，外部留存与权限隔离才提供独立核对点。业务管理员不能删除原始资金流水，调整用冲正并审计。备份恢复需验证序号连续、签名与摘要一致。

快照及请求验签必须处于所有付款必经的执行入口；供应商凭证只供受控执行服务使用，不能保留可绕过校验的普通后台直付入口。若有人已控制执行主机、验签代码或供应商密钥，单一应用内的哈希校验无法保证阻止付款；需要执行服务、密钥权限和独立监控的隔离。WebAuthn 可证明凭证对绑定挑战作了签名，不能单独证明被攻陷页面向人展示了真实金额；更高保证需额外可信交易显示或独立复核渠道，单列增强设计。

## 9. 新增验收

1. 多个商户同时进出同一池，序号唯一，前后余额连续，归属不串户；任一步写入失败全部回滚。
2. 同一回调/查单结果重放，只产生一份资金变动；原始时间、记账时间和操作者可追溯。
3. 来源已扣而目标未到，保留在途且不形成重复可用余额；上游余额差异自动建差异单。
4. 财务签署金额 A、目标 X，之后改成金额 B 或目标 Y，执行入口拒绝并产生主管/EO 告警。
5. 数据库订单不变但适配器实际请求被换金额、目标、币种、链或来源 Unit，同样拒绝；修改 payee ID 对应资料也被识别。
6. 同时修改快照及哈希仍无法通过原签名；复制别人的签名、跨订单/跨环境重放和替换公钥均不通过。
7. 校验后并发修改订单、重复点击执行、任务崩溃重启不造成绕过或重复付款。
