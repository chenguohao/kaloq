## 1. 目标与范围

内部版角色分为客户、操作员、审批和系统维护四类：客户为商户，操作员为运营，审批角色包括财务、主管和 EO，系统维护角色包括管理员（Admin）和超级管理员（Root）。围绕一笔商户业务完成资料收集、入金核验、兑换审批、付款、到账确认和结单。

下文业务流程中的“客户”均指商户；“业务”表示业务活动，不单设系统角色。

已确认的平台边界：原始流程中的建群、拉人入群、线下人员分工和需求沟通属于系统外作业，不转化为网站开发功能，也不因此新增服务群管理或需求登记模块。平台功能围绕注册商户、录入信息、生成商户 ID，以及后续实际需要的平台操作展开。下文保留的沟通、指导和发送等业务描述仅说明流程背景；平台需要保存的资料、确认凭证和操作记录另行明确。

覆盖四个阶段：商户建档与开户、业务收集商户资料、法币转数币、数币转法币。本期仅做内部员工后台：商户通过群告知需求和确认，运营代录信息并办理业务；不提供商户注册、登录或自助工作台。商户在本期是业务服务对象，不创建其登录账号。运营登录后看到全部商户列表，可创建商户档案，点进商户进入该商户的服务工作台。

本期延续 [V1 资金路径](fund-flow.md)：Pyvio 负责法币，Actyve 负责数币，Kaloq 记录客户归属和业务账本。截图中的“客户对应账本”不等于给客户新增一个长期数币钱包。

## 2. 角色与职责

| 角色类别 | 角色 | 职责 | 权限边界 |
|---|---|---|---|
| 业务服务对象 | 商户 | 通过群等线下渠道提供资料和需求，确认报价、收款账户及到账结果，由运营录入并保存凭证 | 本期无平台登录和自助操作入口 |
| 操作员 | 运营 | 在平台录入商户资料、查询到账、提交兑换和付款申请、记录处理结果 | 可以查询，不可改账目或直接付款；只可选择本商户已确认的收款目标 |
| 审批 | 财务 | 审批财务资料，核对商户、金额、费用、账户和账本，完成财务审批 | 具体审批额度及是否承担付款执行职责待确认 |
| 审批 | 主管 | 确认报价、审批兑换和付款、复核 | 审批额度及是否可跨团队审批待确认 |
| 审批 | EO | 超过规定金额时增加审批 | 金额门槛和授权范围待确认 |
| 系统维护 | 管理员（Admin） | 系统管理与维护 | 具体维护范围及与 Root 的权限边界待确认 |
| 系统维护 | 超级管理员（Root） | 系统最高级管理与维护 | 具体维护范围及授权机制待确认 |

付款执行是流程中的执行环节，不另设“付款执行人员”角色；自动执行方式或人工执行权限的归属待确认。系统维护角色不因维护身份自动取得业务审批或付款权限。

已确认：审批为个人专属，每个人只能查看和处理分配给自己的审批，看不到其他人的审批；消息中心、首页待办、审批列表、详情及个人审批记录按本人隔离。同角色人员及 Admin、Root 不默认拥有查看他人审批的权限。

建议：提交人不得审批本人申请；执行权限与提交权限分开。具体不相容岗位和替岗机制待业务确认。

## 3. 商户建档与信息管理

业务人员在线下自行建群、分工、沟通需求。这些步骤不进入本模块的功能清单。

| 平台功能 | 系统行为 |
|---|---|
| 创建商户档案 | 已确认由内部运营在 Kaloq 创建商户记录，不提供商户自助注册 |
| 录入基本信息 | 保存商户主体、联系人等基本信息，校验必填项 |
| 生成唯一商户 ID | 注册记录创建时由系统生成，后续资料、订单、账本均通过该 ID 关联 |
| 查看及修改基本信息 | 在授权范围内维护商户资料，涉及已审核资料的变化遵循版本及复核规则 |
| 查询商户列表 | 运营登录后的首页展示全部商户，可按商户 ID、名称及状态搜索筛选；点击进入该商户服务工作台 |
| 管理商户状态 | 展示、维护平台服务状态，并与通道开户状态区分 |
| 关联商户账本 | 将商户 ID 与对应账本关联 |
| 关联通道账户 | 保存 Pyvio Unit／Client 等通道标识与商户 ID 的映射 |

平台建档与供应商开户是不同动作：本模块生成 Kaloq 商户 ID；提交 KYC/KYB 后由 Pyvio 返回的 Unit／Client ID 在通道开户功能中处理，不能直接替代商户 ID。报价记录及确认归入报价模块，不放在商户建档表单中。

## 4. 客户资料与收款目标

| 资料类型 | 图中要求 |
|---|---|
| 个人 KYC | 护照、住址、人脸识别 |
| 企业 KYB | 按上游要求收集企业及相关人员资料 |
| 银行账户 | 区分客服入账账户与收款账户；原图“客服入账账户”含义待确认，开发时需明确付款来源与收款目标 |
| 数币钱包 | 币种、链、完整地址 |
| 客户确认 | 客户邮件确认并存档 |
| 内部审核 | 运营录入系统，财务审批 |

收款资料必须绑定客户编号，不能串用其他客户资料。修改首款资料时，需重新联系客户确认并重复复核。

建议将上述修改复核规则扩展至所有已确认收款资料，并保留资料版本、客户确认邮件、内部审核记录和生效时间。付款申请引用具体版本，避免资料修改后悄然改变已审批订单。

## 5. 法币转数币流程

| 步骤 | 操作与核验 | 放行条件或异常处理 |
|---|---|---|
| 1. VA 开户 | 提交资料，跟踪审核结果 | 通过：开通账户；补件：通知客户补充；未通过：暂停开户 |
| 2. 核对 VA 后发客户 | 核对账户信息，客户确认后打款 | 保留发出版本与客户确认记录 |
| 3. 查询 Pyvio 收款 | 确认查询入库，核对实际流水，不能只看客户截图 | 付款人或金额不符，先暂停处理；运营只查询，不可改账目和付款 |
| 4. 提交汇款申请 | 运营提交，先冻结对应额度；财务核对客户、金额和费用，主管审批 | 冻结成功且所需审核通过，方可执行；本步具体对应哪段通道动作待确认 |
| 5. 查询 Actyve 到账 | 运营查看兑换结果、实际币数和费用；财务核对 Kaloq 账本 | 确认本笔可用余额可用于付款，不能仅凭上游付款成功推断已到账 |
| 6. 提交数币付款申请 | 运营只选客户已确认的收 U 地址；财务核对客户原始指令、可用余额、金额、币种、链和完整地址；主管审批 | 超过规定金额增加 EO 审批；测试要求满足后，由付款服务执行 |
| 7. 确认付款与客户到账 | 查本次下发订单、实际地址和链上记录，向客户发付款凭证并确认到账 | 有问题返回第 5 步核查；未收到时查询实际付款平台，Actyve 出款找 Actyve，其他钱包找对应方 |
| 8. 服务完成 | 核对 Kaloq 账本的入款、兑换、费用、付款和剩余余额 | 无差异后结单 |

### 5.1 测试钱包与付款变更

截图要求首次地址、大额等情形先测试 3–5 U；金额按收款区块链最低入账要求确定，并与上游固定表对应。测试转账也需要审批，客户确认收到后才算完成。应提前告知客户测试是否计入总额，以及费用由谁承担。

“3–5 U”是图中的参考范围，不作为统一硬编码值。首次地址的判定范围、大额标准、最低入账表、测试款如何计入总额及费用承担规则均待确认。

批准后的金额、币种、链、地址需要变更时，必须重新审批。超时或结果不明时先查订单，不直接再付。

## 6. 数币转法币流程

| 步骤 | 操作与核验 | 放行条件或异常处理 |
|---|---|---|
| 1. 客户审核及收款账户确认 | 客户审核通过，收款银行账户被法币平台接收后，再让客户转币 | 确保客户有能收法币的账户；“被平台接收”的准确状态待确认 |
| 2. 确定客户转出钱包 | 确认币种和链，便于后续核对入账 | 保留客户来源钱包信息 |
| 3. 确认 Actyve 入币地址 | 核对客户、币种、链、地址和 Tag 等 | 通过接口为客户生成专用地址；截图注明 24 小时后归集至主账户，实际周期以通道确认结果为准 |
| 4. 指导客户充值 | 转币前确认报价或计价方式、有效期、费用和法币净收金额 | 大额按规定先测试，确认到账后再转余额 |
| 5. 确认数币到账 | 运营查链上记录和状态，不能只看客户截图；财务核对客户归属、金额和账本 | 错链、少款、多款及无法归属进入异常处理，处置规则待确认 |
| 6. 申请 A2P 兑换 | 运营发起，先冻结对应金额；财务核对报价、金额和费用；主管审批 | 报价过期或条件变化，重新取得客户确认 |
| 7. 检查 Pyvio 法币到账 | 确认兑换成功、法币可用，记录金额和费用 | 到账 Pyvio 主账户后转给子账户；分发成功才可用于客户付款 |
| 8. 提交法币出款申请 | 运营只选客户已确认银行账户；财务核对原始资料、户名、账号、金额和费用；主管审批，大额增加 EO 审批 | 冻结付款余额后执行；账户或金额改变，重新审批。截图将冻结机制标为疑问，需确认具体方案 |
| 9. 客户确认到账 | 留存上游付款记录，向客户发送凭证 | 未收到：联系 Pyvio 查询原付款，不直接再付，并核对是否需补资料；已收到：核对账本、记录退差并结单 |

“退差以后结单”的退差触发条件、对象、币种、审批和执行方式待确认，不能自动当作可直接退款的指令。

## 8. 数据与状态设计（建议）

每笔业务订单至少关联：客户编号、方向、经办人、客户原始指令、报价版本、资料版本、来源流水、兑换单、付款单、测试单、审批记录、冻结记录、上游订单编号、链上交易编号、客户确认与最终对账结果。

新增关联：不可变审批快照及哈希、审批人签名和公钥版本、最终请求摘要、总池流水序号及前后余额、商户分账、执行追踪 ID、安全告警与处理记录。快照还应覆盖币种、网络、来源账户、费用及资料版本，避免只签订单号、金额和地址而遗漏其他关键付款条件。

业务状态、审批状态、资金状态分别记录，避免一个“成功”覆盖所有环节：

- 业务：待资料 → 待入金 → 待核验 → 待兑换 → 兑换处理中 → 待付款 → 付款处理中 → 待客户确认 → 待对账 → 已结单；异常进入暂停处理。
- 审批：待财务 → 待主管 → 待 EO（适用时）→ 已批准，另设退回、拒绝和作废。财务属于审批角色，审批前完成资料与账务复核。
- 资金：可用、冻结、在途、已扣款、已释放；兑换与付款分阶段记录，不把上游已扣款资金提前释放成客户可用余额。

上述为初步模型，并非要求所有订单机械经过相同节点。测试付款、补件、重新报价可作为独立关联记录。

冻结建议使用客户账本中的原子预占，防止重复申请占用同一余额。兑换结束后核销本阶段冻结，按实际到账形成下一阶段余额；付款时另行冻结，避免同笔资金重复冻结。失败、撤销时只释放已确认可释放部分；结果未知继续查询，不能仅因超时解冻或重付。最终账务方案待确认。

## 9. 关键验收条件

| 编号 | 场景 | 预期结果 |
|---|---|---|
| A01 | 运营尝试修改账目或直接付款 | 服务端拒绝，保留审计记录 |
| A02 | 为客户选择另一客户的银行账户或钱包地址 | 服务端拒绝，不依赖前端筛选 |
| A03 | 已确认收款资料被修改 | 重新客户确认与内部复核；旧申请不能无提示改用新资料 |
| A04 | 只有客户截图，尚无可核对的实际收款记录 | 不放行兑换或付款 |
| A05 | 付款人或金额与客户指令不符 | 暂停处理，记录差异和处置结果 |
| A06 | 所需财务、主管或 EO 审核未完成 | 不允许执行；门槛按确认后的配置判断 |
| A07 | 同一可用余额被并发申请使用 | 不能超额占用；冻结规则确认后验证 |
| A08 | 本笔 Pyvio 付款成功，但 Actyve 尚无可核对到账 | 不认定可付 U |
| A09 | 需要测试但客户尚未确认测试到账 | 不放行后续主付款 |
| A10 | 审批后金额、币种、链、地址或银行账户改变 | 原审批失效，重新审批 |
| A11 | 报价过期或条件改变 | 重新取得客户确认，再按规则复核 |
| A12 | 付款超时、结果未知或客户表示未收到 | 查询原订单并跟进，不直接重复付款 |
| A13 | 重复通知或重复点击执行 | 同一笔业务不重复记账或出款 |
| A14 | A2P 仅到 Pyvio 主账户，尚未分发子账户 | 客户可用余额不提前增加 |
| A15 | 客户确认收到但账本存在差异 | 不结单；差异解决并核对完成后结单 |
| A16 | 多商户并发使用总池 | 池流水前后值连续，余额和商户分账同事务更新，失败回滚、重复事件不重记 |
| A17 | 审批后修改金额或收款方，或只替换最终接口参数 | 个人签名或快照比对不通过，不调用通道，并向主管及 EO 发送安全告警 |
| A18 | 同时修改订单快照与哈希，或重放他人签名 | 原签名验证或身份/版本/挑战校验失败，不得执行 |
| A19 | 通道实账、总池账本或商户分账不符 | 形成对账差异及告警，保留证据，按规则阻断并处理 |

其中建议性权限分离、状态和冻结规则，应在业务确认后成为正式开发验收基线。

## 10. 需要业务确认的事项

1. **业务边界**：内部版首期是否仅做法转数和数转法？收 U、U 卡及其他需求是否只登记？法币、币种及网络是否沿用 V1 范围？
2. **角色权限**：四类角色及其成员已确定；待确认各审批角色的额度和数据范围、Admin 与 Root 的维护边界、付款执行方式及权限归属，以及角色兼任和提交／审批／执行的分离规则。
3. **报价**：当日报价与单笔锁价的关系、计价方向、有效期、服务费与通道费、客户确认方式。
4. **大额规则**：触发测试及 EO 审批的金额、币种、等值换算、单笔或累计口径；两条方向是否一致？
5. **测试规则**：首次地址按客户还是全平台判定；最低入账表由谁维护；3–5 U 如何选；数转法测试金额如何确定；测试是否计入总额、费用由谁承担？
6. **冻结机制**：冻结对象、金额是否含费用、兑换与付款的转换时点、驳回及失败释放条件；数转法出款处原图明确留有疑问。
7. **法转数第 4 步**：“汇款申请”对应商户至主账户划转、P2A，还是两者合并审批？执行与审批如何关联？
8. **资料规则**：“客服入账账户”的准确含义；“修改首款资料”的规则是否适用于所有收款资料；邮件确认是否为唯一有效渠道？
9. **到账判定**：银行账户被法币平台接收、链上确认数、Actyve 可用余额和归集状态分别以什么接口及状态为准？
10. **异常处置**：付款人不符、错链、少款、多款、补件、退差、撤销的负责人和审批流程。
11. **结单标准**：是否必须客户明确确认，超时未回复如何处理，剩余余额如何留存或退回。
